# Remote

Swift: `apps/chau7-macos/Sources/Chau7/Remote/` (6 files, 2330 lines), plus `Chau7Core/RemoteFrame.swift`, `FrameParser.swift`, `RemoteActivityState.swift`, `RemoteInteractivePrompt.swift`, `InteractivePromptDetector.swift`, `RemoteOutputBuffering.swift`, `RemoteProtection.swift`, `RemoteTerminalGridSnapshot.swift`, `Telemetry/RemoteClientTelemetryEvent.swift`, and `Settings/Views/RemoteSettingsView.swift`
Swift tests: `Remote/RemoteFrameTests`, `Terminal/FrameParserTests`, `Remote/RemoteTabRegistryTests`, `Remote/RemoteOutputBufferingTests`, `Remote/RemoteTerminalGridSnapshotTests`, `Remote/InteractivePromptDetectorTests`, `Remote/RemoteInteractivePromptTests`, `RemoteActivityStateTests`, `Terminal/RemoteProtectionTests`, `Remote/RemoteClientTelemetryEventTests`, `Remote/RemoteViewerModeTests` (app target only, not run by `swift test`)
Wave: 3
Depends on: Overlay (tab list, selection), Terminal (output tap, text and grid snapshots, input), MCP (command approvals), AI (activity status, tool names), Settings, Telemetry (stores iOS client events). Runtime dependency: the Go agent `services/chau7-remote` and the Cloudflare relay `services/chau7-relay`.

Lets the user watch and drive Chau7 tabs from the Chau7 iOS app over the internet. The Mac app runs a Go helper (`chau7-remote`) that holds the relay WebSocket and does pairing and end-to-end encryption; the Mac app talks to that helper over a local Unix socket and decides what the phone sees (tab list, output of the selected tab, AI activity, approval requests, interactive prompts) and what the phone may do (switch tab, type, answer approvals).

## Notes

**Architecture.** `iOS app <-> relay (Cloudflare Worker + Durable Object) <-> chau7-remote (Go) <-> Chau7 (Unix socket) <-> PTY`. The Swift app is the IPC *server* (binds `remote.sock`, `listen(1)`); the Go agent is the *client* and reconnects every second. The agent is cross-platform Go except `machineUUID()` (`ioreg`, macOS only), so Chau7 Next can launch the same binary.

**Chau7 Next isolation (DUAL-SHIP.md).** Use `~/Library/Application Support/Chau7 Next/remote.sock` and `.../Chau7 Next/chau7-remote`. The agent's state file defaults to `~/.chau7/remote/state.json` when `CHAU7_REMOTE_STATE` is unset, and the Swift app never sets it (it reads `RuntimeIsolation.chau7Directory()/remote/state.json`). Chau7 Next must pass `CHAU7_REMOTE_STATE` pointing into its own data root, otherwise both apps share one device ID, key pair and paired-device list. Pass a `CHAU7_MAC_NAME` that says "Chau7 Next" so the iOS app can tell the hosts apart (it is sent as `mac_name` in `PAIR_ACCEPT`). Add these paths to `DataRoot`; `remote.sock` is already on the forbidden-string list in `data_root.rs`.

**No Keychain in practice.** The spec says keys are persisted in the Keychain; the actual implementation keeps the Mac private key in `state.json`, AES-wrapped with `SHA256("chau7-key-wrap:" + IOPlatformUUID)` (`key_encrypted: true`). `relay_secret` is only read from that file (no UI). Nothing in this module touches the Keychain.

**Frame format** (all little-endian, `Chau7Core/RemoteFrame.swift`, agent `internal/protocol/frame.go`): 20-byte header `version u8 (=1) | type u8 | flags u8 (bit0 = encrypted) | reserved u8 | tab_id u32 (0 = active tab) | seq u64 | payload_len u32`, then payload. On the Unix socket each frame is prefixed by `u32 LE frame_len` (header + payload); lengths 0 or above 5 MB are skipped by dropping the 4-byte prefix. The Mac sends `flags = 0` and its own `seq` counter starting at 1; the agent encrypts toward the relay.

**Frame types.** `0x01 HELLO`, `0x02 PAIR_REQUEST`, `0x03 PAIR_ACCEPT`, `0x04 PAIR_REJECT` (relay only, handled by the agent); `0x05 SESSION_READY` (agent to Mac), `0x10 TAB_LIST`, `0x11 TAB_SWITCH`, `0x12 ACTIVITY_STATE`, `0x13 ACTIVITY_CLEARED`, `0x14 CACHED_TAB_LIST` (defined, never sent by Swift), `0x15 INTERACTIVE_PROMPT_LIST`, `0x20 OUTPUT` (raw PTY bytes), `0x21 INPUT` (UTF-8), `0x22 SNAPSHOT` (UTF-8 buffer text), `0x23 TERMINAL_GRID_SNAPSHOT`, `0x30 PING`, `0x31 PONG`, `0x40 PAIRING_INFO`, `0x41 SESSION_STATUS`, `0x42 REMOTE_TELEMETRY`, `0x43 CLIENT_STATE`, `0x50 APPROVAL_REQUEST`, `0x51 APPROVAL_RESPONSE`, `0x7F ERROR`. Mac to agent: 0x10, 0x12, 0x13, 0x15, 0x20, 0x22, 0x23, 0x31, 0x50, 0x7F. Agent to Mac: 0x05, 0x11, 0x21, 0x30, 0x40, 0x41, 0x42, 0x43, 0x51, 0x7F.

**JSON payloads** (snake_case keys, exactly as in `RemoteControlModels.swift`):
- `PAIRING_INFO`: `device_id, mac_pub, pairing_code, expires_at, relay_url`. The QR / "Copy Pairing JSON" payload is the same five keys, encoded in the order `relay_url, device_id, mac_pub, pairing_code, expires_at`.
- `SESSION_STATUS`: `status` (`connecting|ready|disconnected`), `paired_device_id`, `paired_device_name`. On `ready` the Mac sends its initial state.
- `TAB_LIST`: `{"tabs":[{tab_id, title, project_name, branch_name, is_active, is_mcp_controlled}]}`. Tab IDs start at 1, are kept per tab UUID for the life of the app and are never reused.
- `TAB_SWITCH`: `{tab_id}`. `ERROR`: `{code, message}` (Mac sends JSON; incoming error payload is shown as plain text).
- `CLIENT_STATE`: `app_state (foreground|background), stream_mode (full|approvals_only), push_token, push_topic, push_environment (development|production), notifications_authorized`.
- `APPROVAL_REQUEST`: `request_id, command, flagged_command, timestamp (ISO 8601), tab_title, tool_name, project_name, branch_name, current_directory, recent_command, context_note, session_id`. `APPROVAL_RESPONSE`: `request_id, approved`. Request IDs are UUID strings; protected-input approvals use their own IDs.
- `ACTIVITY_STATE`: `activity_id ("tab-<id>-approval" or "tab-<id>-pane-<uuid lowercase>"), tab_id, tab_title, tool_name, project_name, session_id, status (idle|running|waitingInput|completed|failed), headline, detail, is_selected_tab, started_at, updated_at, approval {requestID, command, flaggedCommand}`. Dates use Swift's default `JSONEncoder` (seconds since 2001-01-01 as a number), and `status`/`approval` use Swift case names, not the snake_case values in the spec. Match the Swift output, not the spec, until the iOS app changes. `ACTIVITY_CLEARED` has an empty payload.
- `INTERACTIVE_PROMPT_LIST`: `{"prompts":[{id, tab_id, tab_title, tool_name, project_name, branch_name, current_directory, prompt, detail, options:[{id, label, response, is_destructive}], detected_at}]}`; `id = "tab-<id>-pane-<uuid>-<signature>"`, signature = base64 of the first 12 bytes of SHA-256 over prompt + options; `detected_at` uses the default Date encoding.
- `REMOTE_TELEMETRY`: see Telemetry.md (TEL-015).

**Grid snapshot `CHG1`** (`RemoteTerminalGridSnapshot.swift`), 29-byte header: `"CHG1" | version u8 (=1) | cols u16 | rows u16 | cursor_col u16 | cursor_row u16 | cursor_visible u8 | 3 zero bytes | scrollback_rows u32 | display_offset u32 | cells_byte_count u32`, then `cols*rows` cells of 16 bytes each: `character u32 | fg r,g,b | bg r,g,b | flags u8 | underline-variant u8 | link_id u16 | 2 padding bytes` (same layout as `RustCellData` / `chau7_terminal` `CellData`). Chau7 Next uses the same emulator, so it can copy the grid buffer directly.

**Behavior details.** Output is only forwarded for the selected tab and only in `full` mode; output for other tabs is dropped, not queued. The background snapshot prefetch is a no-op (cancelled immediately). The input path has no rate limit and no newline handling (the phone appends `\n`). MCP approvals raised while the agent is not connected to `remote.sock` are not registered, so they are never resent later (only registered contexts are resent on reconnect). `RemoteProtection` is a speed bump, not a sandbox; the phone approval is the real gate.

**Viewer mode (RMT-027, RMT-028)** is a skeleton: `broadcastToViewers` only logs, nothing calls `handleViewerConnection`, and `RemoteViewerStatusView` is not placed in any view. Settings keys: `feature.remoteViewer`, `remoteViewer.maxViewers`, `remoteViewer.autoApproveKnown`, `remoteViewer.knownIDs`. Decision (2026-10-10): port as designed. Chau7 Next follows `RemoteViewerModeTests`, which reject a viewer arriving at the maximum (the Swift code queues it).

**Settings keys.** `remote.enabled` (default false), `remote.relayURL` (default `wss://relay.example.com/connect`). Both are part of the settings export/import JSON, not of `config.toml`.

**RMT-029 n/a:** Chau7 Next starts with its own empty state file, so there is no single-device legacy state to read; the agent itself still writes the legacy fields.

**RMT-030 current implementation.** Next validates the opened credential descriptor
(no-follow, nonblocking, current owner, regular file, 0600/0400 and at most
8192 bytes), canonical distinct 32-byte role keys and matching public identity.
Only public metadata leaves the validator. The identity helper receives an
explicit Next-owned `--state`; failures contain quoted identity/provision
instructions and no credential contents. Binary sync/build, identity/provision
validation, process spawn and paired-device reads run off the UI thread;
generation guards reject completions after relay changes, disable or quit.
Owned helper shutdown is asynchronous. Non-Unix builds explicitly report the
unsupported owner/mode boundary of the current Go relay helper rather than
claim validation. No production relay pairing is claimed by local tests.
