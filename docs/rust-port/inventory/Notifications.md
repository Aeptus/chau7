Turns events from AI tools, the shell and the app into user feedback. Each event is matched to a trigger, checked against per-trigger conditions (Focus/DND, app focus, active tab) and a rate limiter, routed to the tab it belongs to, then delivered by a list of configurable actions: a system notification, a tab style or badge, a sound, a dock bounce, a script, a webhook and about twenty more. Every delivery is recorded in an in-memory ledger shown in Settings and the debug console.

Pure logic lives in `Chau7Core` (`NotificationTriggerCatalog`, `NotificationActionCatalog`, `NotificationStylePlanner`, `NotificationDeliverySemantics`, `NotificationEventPreparation`, `Notifications/` canonical model and ingress); the app side is `NotificationManager` (delivery), `NotificationPipeline` (decision), `NotificationActionExecutor` (actions) and `TabResolver` (routing).

## Notes

- Chau7 Next: the engine is `chau7_next::notifications` (entry point `notifications::ingest(event, cx)`, see its module doc); pure logic in `chau7_next_core::notifications`. Every event on the AI event feed (`ai::events_out`) enters the engine once (subscribed in `chau7_next/src/seams.rs`): shell events of each session (`ShellEventDetector`: `exit_code_match`, `command_failed`, `command_finished`, `process_ended`, configured by `notification_shell_events`), so a failed command in a background tab notifies by default, plus the AI event logs, Claude Code hooks, history idle notices and file conflicts.
- Events carry tab ids as `tab_resolver::tab_uuid(TabId)`. Settings are stored as JSON in `[next]` of `config.toml` (`notification_rules`, `notification_shell_events`, `notification_app_events`).
- Not bundled (`cargo run`) banners use the AppleScript fallback; Swift skips notifications entirely there. On Linux and Windows the fallback is GPUI's system notification.
- NOT-016/017/039: the success/error style on command end (NOT-039) is a Chau7 Next behavior with no exact Swift counterpart (Swift's style planner does not map `command_failed`); kept.
- Decision order (`NotificationPipeline.evaluate`): trigger lookup (exact then wildcard) -> enabled (3 tiers: per-trigger override, group override, default) -> conditions (per-trigger, then group, then default) -> actions (per-trigger, then group, then show notification) -> if tab is active and "only when tab inactive", style-only -> single default show-notification uses the native path. Rate limiting is applied after the decision, by the caller.
- Settings keys live in `FeatureSettings.notificationSettings` (`triggerState`, `triggerConditions`, `triggerActionBindings`, `groupConditions`, `groupActionBindings`) and `shellEventConfig`. The Swift app stores them in UserDefaults; Chau7 Next should put them in its own `config.toml` section.
- Action list (25): showNotification, playSound, focusWindow, dockBounce, badgeTab, styleTab, runScript, runShortcut, executeSnippet, webhook, sendSlack, sendDiscord, dockerBump, dockerCompose, kubernetesRollout, copyToClipboard, writeToFile, openURL, gitCommit, voiceAnnounce, flashScreen, menuBarAlert, startTimer, stopTimer, logTime. Docker and kubectl default paths are `/usr/local/bin/...`.
- NOT-021/023/025/029/031/032/033 need a platform trait (macOS implementation, stub or best effort elsewhere). Chau7 Next already uses `gpui::SystemNotification` for NOT-001; DND (NOT-005) and permission state (NOT-003) have no equivalent in the Chau7 Next code yet.
- Notification clicks are not handled in Swift (no `didReceive` handler), so clicking a banner only activates the app.
- Overlapping rows in other inventories (update both when porting): NOT-003 with SET-119; NOT-016 with OVL-069; NOT-009/011/035/036/037 with SET-120 to SET-128; NOT-038 with the Events inventory.
